# Дашборд FBS · EPIC LOVE

Каждый час GitHub Actions забирает из API продавца Wildberries сборочные задания,
статусы заказов и состояние поставок по бренду и публикует страницу на GitHub Pages.
Компьютер для этого включать не нужно.

В отчёт попадает только **FBS** — заказы со склада продавца (`/api/v3/*`, модель
«сборочные задания»). FBW тут нет вообще.

---

## Что на странице

**Таймер сборки.** Каждое задание с моментом заказа, дедлайном и остатком времени.
Часы тикают в браузере в реальном времени, сами данные обновляются раз в час.
Дедлайн = момент заказа плюс `assembly_deadline_h` из `config.json` (по умолчанию 48 ч,
как срок отгрузки FBS у WB). Если у ваших складов срок другой — см. раздел «Обслуживание».

**По артикулам.** Сколько заказов каждого артикула в очереди сборки, сколько просрочено,
сколько уехало в поставку, принято WB, выкуплено и отменено. Плюс заказы за 24 часа,
7 и 30 дней.

**Поставки.** Черновик (можно докладывать заказы) → отгружается (закрыта, едет на склад
WB) → принята (отсканирована на приёмке). Отклонённые поставки помечаются отдельно.

**Остаток FBS по складам.** Сколько единиц бренда лежит на каждом складе продавца,
с разбивкой по артикулам и размерам. Заказ уходит на тот склад, где есть остаток, —
отсюда видно, куда именно поедут сборочные задания.

**Все заказы.** Полный список с поиском по артикулу, номеру заказа и номеру поставки,
с фильтром по стадии. Рядом со «стадией» показаны и технические статусы WB —
`supplierStatus` и `wbStatus`, — чтобы можно было сверяться с личным кабинетом.

## Кнопка «обновить»

Страница статическая, пересборку делает GitHub Actions. Кнопка **обновить** в шапке
открывает вкладку запуска workflow — там нужно нажать зелёную кнопку **Run workflow**.
После этого страница сама раз в 20 секунд проверяет, не собралась ли новая версия;
как только собралась, кнопка становится зелёной — клик по ней перезагружает страницу
со свежими данными. Прогон занимает 2–5 минут.

Без нажатий страница всё равно проверяет свежесть раз в три минуты, так что открытую
на складе вкладку не нужно обновлять руками — она сама подсветит, что данные поменялись.

Одним кликом запустить пересборку прямо со страницы нельзя: для этого в неё пришлось бы
зашить токен GitHub, а страница публичная.

## Настройка — один раз

### Быстрый путь

Двойной клик по `ЗАПУСТИТЬ_ДАШБОРД.command`. Скрипт войдёт в GitHub по восьмизначному
коду, создаст репозиторий, зальёт код, пропишет секрет с токеном, включит Pages
и запустит первую сборку. В конце покажет ссылку.

### Руками

1. Новый **публичный** репозиторий на GitHub (бесплатный Pages работает только с публичными).
   Залейте туда содержимое папки `wb-fbs-epic-love`.
2. `Settings → Pages → Source: **GitHub Actions**`.
3. `Settings → Secrets and variables → Actions → New repository secret`:

   | Секрет | Что класть |
   | :-- | :-- |
   | `WB_TOKEN` | Персональный токен кабинета WB |

4. `Actions → FBS dashboard → Run workflow`.

Токен нужен **Персональный**, с категориями **Маркетплейс** (сборочные задания, поставки,
статусы), **Контент** (карточки, фото, названия) и желательно **Статистика**.
Права только на чтение — скрипт ничего не пишет в кабинет. Живёт токен 180 дней.

## Как это устроено

| Файл | Зачем |
| :-- | :-- |
| `wb_client.py` | HTTP к WB: `Authorization` без `Bearer`, честная отработка 429 по `X-Ratelimit-Retry` |
| `collect.py` | Выгрузка: очередь сборки, инкремент по заказам, статусы, поставки, карточки |
| `aggregate.py` | Стадии, таймеры, свод по артикулам и поставкам → `data/dashboard_data.json` |
| `render.py` | Данные + вёрстка → `dist/index.html` |
| `template.html` | Сама страница |
| `config.json` | Бренд, префиксы артикулов, срок сборки, глубина истории |
| `state/` | Заказы, поставки, карточки, остатки, курсоры. Коммитится в репозиторий и живёт между прогонами |

### Почему выгрузка устроена именно так

Кабинет мультибрендовый: 250 брендов, больше 40 000 карточек, десятки тысяч заказов
в сутки. Фильтра по бренду в API заказов нет, поэтому перебирать всю историю каждый час
невозможно — упрёмся в лимиты. Схема такая:

1. `/api/v3/orders/new` — одним запросом вся очередь сборки кабинета, фильтруем
   по префиксу артикула из `config.json`;
2. `/api/v3/orders` — инкремент с сохранённой позиции курсора, не больше
   `max_pages_per_run` страниц за прогон. Отсюда берётся номер поставки и те заказы,
   которые успели уехать в поставку между прогонами;
3. `/api/v3/orders/status` — статусы всех отслеживаемых заказов бренда, пачками по 1000;
4. `/api/v3/supplies/{id}` — состояние только тех поставок, где лежат заказы бренда;
5. `/api/v3/stocks/{warehouseId}` — остатки бренда по складам продавца: полный обход
   раз в `stocks_full_refresh_hours` часов, между обходами проверяются только склады,
   где остаток уже есть;
6. `content-api` — карточки бренда: фото, предмет, штрихкоды. Новые карточки находятся
   просмотром свежеобновлённых страниц кабинета, недостающие размеры и штрихкоды
   добираются точечно поиском по полному артикулу.

Состояние лежит в `state/` и коммитится обратно в репозиторий, поэтому каждый прогон
продолжает с того места, где остановился предыдущий. Первый прогон разбирает историю
за `backfill_days` дней и может занять несколько запусков — на странице в это время
висит пометка, что история ещё догоняется.

## Обслуживание

**Другой срок сборки.** `config.json`, поле `assembly_deadline_h`. Если у разных складов
разный срок — `warehouse_deadline_h`, где ключ это `warehouseId` со страницы:

```json
"warehouse_deadline_h": { "1950095": 24, "1790430": 72 }
```

**Добавились артикулы бренда.** Ничего делать не нужно: заказ попадает в отчёт, если
артикул начинается с префикса из `article_prefixes` или если карточка с таким `nmID`
известна как карточка бренда. Список карточек скрипт сам обновляет раз в 12 часов,
просматривая свежеобновлённые карточки кабинета.

**Сменился бренд или нужен второй.** `config.json`: `brand` и `article_prefixes`.
Затем удалите `state/orders.json`, `state/supplies.json`, `state/cards.json` и
`state/cursor.json`, чтобы история собралась заново.

**История догоняется слишком долго.** Поднимите `max_pages_per_run` (одна страница —
1000 заказов кабинета, примерно 2–5 секунд с учётом пауз). Или запустите workflow
руками, указав `max_pages` побольше.

**Сменить частоту.** Строка `cron: "23 * * * *"` в `.github/workflows/dashboard.yml`.
GitHub может задержать запуск на 5–30 минут при высокой нагрузке — это его штатное
поведение, не поломка.

**Токен протух.** Живёт 180 дней. Сборка упадёт — выпустите новый и обновите секрет
`WB_TOKEN`.

## Про приватность

Страница помечена `noindex` и в поиск не попадёт, но **пароля на ней нет**: кто знает
адрес, тот видит цифры. Токен в репозиторий не уезжает — он в `.gitignore` и живёт
в секретах GitHub. Саму папку с `.env` никому не пересылайте.
